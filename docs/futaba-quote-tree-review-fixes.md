- `b558b62` の起動復元・新着境界修正は維持する。レビュー開始時の作業ツリーはclean、`feature/futaba-thread-display` はorigin追跡値より4commit先行。

## 仕様変更の扱い

`futaba-quote-tree-worklog.md` と `futaba-quote-tree-worklog-popup.md` に、ユーザー確認による次の仕様変更が記録されている。

- 引用省略はdetailsによる折りたたみではなく、引用元レス番号リンクへ置換する。
- 置換リンクのホバーは親全文ではなく、子が実際に引用した部分だけを表示する。
- 通常のレス番号アンカーは従来の親全文ポップアップを使う。

これを新しい仕様として尊重する。旧計画に合わせて折りたたみへ戻す修正は禁止。交互引用を保持する要件、曖昧な親を決め打ちしない要件は引き続き有効。原文の意味を壊す省略を、UI方式変更で正当化しない。

## 最優先: 株スレ表示不能（P1）

対象URL: https://may.2chan.net/b/res/1432656555.htm

WebツールではURLを取得できなかった。以降はアプリの実ログと保存HTMLに基づく。スレが現在ライブで取得可能かどうかは断定しない。

### 証拠

`src/ChBrowser/bin/Debug/net8.0-windows/data/chbrowser.log`:

- 1603〜1614行付近、11:23:19: キャッシュ990レス、追加5レス、合計995レス取得に成功。
- 1615〜1617行付近: 株スレWebView ready、995レスの再同期をC#側で用意。
- 1625行: 11:23:19.899、JSが株スレの初回990レスバッチを受信。
- その後の株スレ995レス再同期のJS受信記録がない。他タブのログはある。`scrollTarget=null` のため、以前の14億番号スクロール走査とは別問題。
- この区間に株スレの明示的なJS例外・取得失敗は見つからない。複数タブの汎用ログが混在するので、後続の無名 `markNewPosts` 等を株スレ描画完了の根拠にしない。

現在のDebug DLLの **実際の `FutabaThreadClient.Parse`** をリフレクションで呼び、保存HTMLから995投稿を抽出。JS解決器へ渡して次を実測した（Node、DOM無し）。

| 処理 | 実測 |
| --- | --- |
| 995投稿を `resolve` に一度渡す | 153.3ms |
| 先頭から1投稿ずつ追加し実物 `ensureFutabaQuoteRefs` を呼ぶ、100投稿 | 42ms、全件解決100回 |
| 同200投稿 | 328ms、全件解決200回 |
| 同400投稿 | 2630ms、全件解決400回 |
| 同995投稿を8秒上限で検証 | 585投稿・全件解決585回の時点で8009ms、打ち切り |
| 同995投稿を45秒上限で最後まで検証 | **43335ms、全件解決995回、完了** |

これはWebView実画面の所要時間ではない。DOM無しでも43.3秒の同期処理が生じることを再現しており、表示不能の有力原因。実画面の最終確定は修正前後の診断ログで行う。1回目の短い計測と全件計測は別runであり、時間比を厳密な改善倍率として扱わない。

### 原因箇所

- `Resources/thread.js:1249-1281`: `ensureFutabaQuoteRefs` が全投稿・全行の署名を毎回作る。署名が変わると `resolve(allPosts)` を全件実行。
- 同:5121以降: 1投稿ずつ `allPosts.push` → 参照解決／描画が走る。追加のたびに署名が変わる。
- `Resources/futaba-quotes.js:40-59`: 各引用行について全先行投稿・添付・本文行を総当たり。`candidateLines` の正規化も繰り返す。
- 1回の全件解析に概ね二次の要素があり、それを各prefixで繰り返すことで概ね三次の増加を招く。描画・返信数・親取得の読み取りから解析を起動する構造も追加負担になる。

### 修正指示

1. 描画中の `getPostReferences` / `postDataFor` は解決済みMapの読み取りだけにする。そこで全件署名計算・全件解決を開始しない。
2. **最小の復旧策**は、受信バッチの新規投稿を確定後、描画前に参照情報を一度だけ準備すること。単に1投稿追加時の全件解析を別関数に移すのは不可。
3. 後続最適化では正規化行・添付basename・本文候補の索引を保持し、新規投稿を順に追加解決する。順序・同一投稿重複・過去投稿更新を区別する。
4. 新規投稿だけの追加は増分更新。同件数の本文／添付更新、NG除外、スレ変更、resyncは明示的なrevision/dirtyで必要範囲を無効化する。
5. 現署名はattachmentUrlsを含まず、添付変更で誤った親を再利用する。ローカル検証で所有者の `a.jpg` を `b.jpg` に変えても親100が残り、新規resolveでは未解決になることを確認済み。行文字列の連結署名による衝突も避ける。
6. 初回readyの全件resyncは高負荷を二重化し得るが、元の復元バグ対策を根拠なく削除しない。世代・反映済みrevision等で重複処理を避ける案は、cold起動・新着あり・ペイン移動・reloadを通してから採用する。
7. 全件再構築が必要なケースでも処理を計測し、必要なら世代付きで分割してUIへ制御を返す。古い世代の処理が新しいDOMを上書きしないこと。

## 引用データの誤解析（P1）

### C#の閉じタグ・改行処理

箇所: `Services/Api/FutabaThreadClient.cs:25,100-148`。

- `QuoteTagRe` は閉じタグにもclass/color属性がある形を要求している。普通の `</font>` / `</span>` を認識できず、タグ深さが増えたままになる。
- `hasTextualQuoteMarkers` の前処理は `<br>` まで削除してから行頭判定するため、最初の行が非引用で途中から引用が出る本文を正しく判定しない。
- `>No.123` を `quoteDepth=0` に変える処理も構造を壊す。引用の深さと参照の種別は別情報。

実DLLによるサンプル解析で、1432673776の返答2行が引用深さ2、1432664676の通常URL行が引用深さ1になった。目視の推測ではなく解析結果で再現済み。

修正: `<br>` を行境界にしてから判定し、開閉タグを正しく追跡する。明示的な行頭記号の深さを優先する。閉じfontと一般fontの入れ子も区別し、タグ由来の引用状態を後続通常行へ漏らさない。No.参照でも深さを保持する。

受入: 上記実投稿の通常行はdepth=0、`>No.X` は1、`>>No.X` は2。複数行を包む引用タグ、本文→引用→本文、空行、HTMLエンティティを実C# Parseのテストで固定する。

## 多重引用の親誤判定と文脈照合不足（P1）

箇所: `Resources/futaba-quotes.js:20,30-37,54-65`。

1. No.参照を深さ判定より先に解決しているため、祖先から継承された `>>No.X` も直接親になる。
   - 実投稿1432667966は直接親1432667645だけでよいが、現在 `[1432667536,1432667645]` を返す。
   - 既存の「親が複数なら根」ルールに入り、会話のツリーが途切れる。
2. 深い引用の本文は読み飛ばすだけで、候補の絞り込みに使っていない。
   - 異なる元文脈を引用して同じ返答を書いた2投稿に対し、子がその片方の元文脈を二重引用しても未解決になることを合成fixtureで再現した。
   - 旅行の単純テストが通るのは、直近の返答文自体が一意だから。文脈照合を実装できた証拠にならない。

修正: 引用記号をちょうど1段除いた行列を親候補の引用深さ付き本文へ照合する。深いNo./画像名は文脈にだけ使う。行単位候補の単純なunionで済ませず、順序付きブロックで候補を絞る。候補がなお複数なら未解決。既存の多対象参照は維持する。

受入: 実投稿1432667966の親が `[1432667645]`。文脈のみで一意にできる例はresolved、文脈も同じなら未解決。各行の対応元を出力して表示処理でも利用する。

## 交互引用を消してしまう（P1）

箇所: `Resources/thread.js:1174-1212`、`buildFutabaDisplayBody`。

最初の連続引用prefixだけ数え、後ろに引用が再出現するか確認しない。実投稿1432662652を実関数に渡すと、次のように最初の引用だけがリンクへ置換される（本文描画ヘルパだけスタブ化して分岐を検証）。

```text
[親リンク]
うん
>インドで積立てる
ので！？
```

最初の「NISAでS&P500とかオルカンや」が失われ、当初から明示された保持要件に反する。解決器はこの投稿をresolvedとするため実際に置換対象になる。

修正:

- 非引用の返答を挟んで引用が再出現する場合は、引用リンクへの置換を行わず全文を表示する。
- 渡された `context` が未使用。表示中の親が存在するか、フィルタ/NGで文脈が失われていないかも確認する。
- `isEmbedded=true` ならflat中のポップアップでも置換が許可される現条件を分離する。通常の親全文ポップアップは本当に全文を出し、置換リンク専用の引用プレビューだけ別経路にする。
- 全て引用の投稿をリンクだけに変える処理も見直す。複数親へのリンクすべてに同じ引用prefixを付けず、引用行と親の対応情報からプレビューを作る。
- `Body` は保持していてもDOMからのコピー・閲覧時の文脈が変わるので、データ不変だけで合格にしない。

受入: NISA例の4行は両ツリーで保持。通常アンカーホバーは全文、置換アンカーホバーはそのリンクに対応する引用部分。親欠落・NG・モード切替でも読めること。

## 重複ありツリーで3段の表示が成立しない（P2）

箇所: `Resources/thread.js:1507-1528,4840-4856,4893-4906`。

- 返信追加は `getElementById('r'+parentNum)` の正本だけへ行われる。
- 親のreverse複製には子を伝播せず、`buildTreePostHtml(..., true)` はleafを返す。
- したがってA→B→C→DのBの複製にC/Dが付かず、A配下で3段の関係を一続きに表示できない。これはコード追跡結果で、今回の実画面確認は未実施。

修正: ふたばの重複ありモードについて、正本を残しつつreverse複製にも必要な子孫を描画する。forward埋め込みを無限に辿らない。深さ・複製数上限と続きの参照を用意し、5ch側の既存表示を巻き添えに変えない。

受入: 旅行の4実投稿を使い、両モードのDOM親子関係を検証する。初回・分割バッチ・新着・resyncで同じ意味の階層となる。正本IDは1つ、複製はID無し。

## 引用プレビューで正本IDが重複する（P2）

箇所: `Resources/thread.js:4450`。`openQuotePreviewPopup` が `postDataFor(sourcePost, false, false, '')` を呼び、プレビューにも `id=r親番号` を出す。

修正: ポップアップは `omitId=true` とし、本文の正本IDと競合させない。data-numberによる操作は維持する。親ヘッダを作るためだけに本文・メディア・引用解決の重い副作用を実行しない構成が望ましい。

受入: 同一投稿を複数ポップアップで開いてもdocument全体の `#r番号` は正本1件。スクロール、返信バッジ、ポップアップ連鎖を確認する。

## 検証不足と実施順序

既存Nodeテスト12件はこのレビューでもすべて成功した。しかし性能・C#実解析・本文省略・両ツリーDOM・実サンプルの多重No.を検証していない。テスト成功だけで上記問題を否定しない。

Lunaへの順序:

1. Git状態と対象commitを確認。製品変更前に最新ログと株スレHTMLのローカルコピーを保全する。
2. P1性能問題を先に最小修正。取得失敗時のキャッシュ表示も成立する状態へ戻す。引用を無条件無効にして完了扱いにしない。
3. C#解析 → 引用解決の順に修正。実サンプルと失敗fixtureを追加してから両ツリーへ統合。
4. 交互引用保持・通常ポップアップと引用プレビューの区別・ID一意性を修正。
5. 重複ありの3段階対応をDOM検証。性能の再退行が無いことも確認。
6. 通常のDebug出力へbuild。明示的な終了コード0、警告0・エラー0を確認。
7. 実行確認は自分のDebug PID・実行パスを記録し、既存のユーザープロセスを無断で巻き込まない。ログにスレキー/世代/件数/解析開始終了/描画開始終了/所要時間を付けて、株スレの後続処理まで追う。
8. 株スレ995件程度のcold起動・キャッシュ・新着・2モード切替・ポップアップを確認。JS解析時間とDOM描画時間を区別して報告。ユーザーの見た目/操作感確認前にcommit/push/merge/releaseしない。

### 性能の合格条件

- フルresolveを1投稿ごとに再実行していないことを呼出し回数で検証する。全件バッチは必要な1回、または新規投稿だけの増分解決。
- このマシン・995投稿のDOM無し解析は暫定1秒以内を目安とする（現在単発153ms）。機種依存の時間だけでなく、全件解析回数と走査量もテストする。
- 本文/添付変更とresync時には正しく再計算される。性能のために署名を件数だけへ戻すのは禁止。
- UI検証ではJSのタイマー応答・新着メッセージ受信・タブ操作が進むこと。1000〜数千投稿のsynthetic入力で上限も測る。
